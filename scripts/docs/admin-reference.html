01 The nine roles

The RBAC pyramid.

Each user has one global role — their default power level outside any specific organization. Inside an org or event, the role is re-derived from their membership there. Same user can be Event Manager in one org and Viewer in another.

EventFlow01 · The roles

The hierarchy at a glance

Super Admin · platform operator
Enterprise AdminEnterprise Manager
Org AdminEvent Manager
CoordinatorFinance ManagerViewer
User · default attendee
Super AdminPlatform operator. Sees every enterprise, org, user, payment, audit log across every tenant. Only role with /super-admin access. Can impersonate other users.
Enterprise AdminOwns an enterprise (e.g. a whole university). Creates and deletes orgs inside it, manages billing, sees cross-org analytics.
Enterprise ManagerEnterprise Admin minus billing and delete. Reads everything, writes most things inside the enterprise.
Org AdminFull read/write inside a single organization. Creates events, invites members, sets up payments and coupons, manages the org's public website.
Event ManagerCreates and runs events, edits registration forms, sends communications. No billing access, no member management.
CoordinatorDay-of-event operations: checks people in, sees the live attendee list. Read-only everywhere else.
Finance ManagerPayments-focused. Refunds, financial reports, coupons, payment analytics. Reads events and registrations but can't edit them.
ViewerRead-only across events, registrations, payments, check-ins, and basic analytics. Cannot change anything. Good for auditors and observers.
UserDefault attendee role. No admin access. Gets /dashboard and the public-facing app.

04 Day in the life

Four real walkthroughs.

Concrete step-by-steps for the four roles that actually spend their day inside the admin. The remaining five either rarely log in or act through one of these.

EventFlow04 · Walkthroughs

Org Admin Running a new event end-to-end

  1. /admin/org/events → Create Event. Fill the six-step wizard.
  2. On Step 6, click Preview — the event opens in a new tab with a yellow Preview mode banner. Confirm the public view looks right.
  3. Back in the wizard, click Publish Event. Confirm the dialog.
  4. /admin/org/coupons → create an early-bird discount scoped to this event.
  5. /admin/org/communications → compose an announcement email with the event link; send to your members or a custom list.
  6. As registrations land, /admin/org/events/[id]/registrations shows them live. Bulk-approve if your event requires approval.
  7. On event day, load /admin/org/events/[id]/check-in on a tablet and scan QRs. Live stats update alongside.
  8. After the event, /admin/org/certificates → bulk-issue certificates. They appear in each attendee's /dashboard/certificates.
  9. Review the debrief on /admin/org/events/[id]/analytics.

Finance Manager Issuing a refund

  1. /admin/org/payments → search by registration number or email.
  2. Click the payment row. A detail drawer opens with amount, method, gateway transaction ID.
  3. Click Process Refund. Enter amount (defaults to full), reason, confirm.
  4. The refund is marked COMPLETED, the registration is cancelled, any coupon use is decremented, the user is notified, and the audit log captures who did what.
EventFlow04 · Walkthroughs

Coordinator Covering the door on event day

  1. /admin/org/events/[id]/check-in on a phone or tablet.
  2. Tap QR Scan. Allow camera access the first time.
  3. Point at each attendee's QR. A green banner confirms a successful check-in.
  4. If a QR won't scan, tap Manual. Search by name, email, or registration number. Click Check In on the matching row.
  5. Live stats at the top — total expected, checked-in, percentage — update as the queue moves.

Super Admin Investigating a reported user

  1. /super-admin/users → search by email.
  2. Click the user row. Review their role, orgs, registrations, payments, login history.
  3. If action is needed: Suspend (reversible, user can't sign in), Ban (permanent without manual unban), or Change Role.
  4. /super-admin/audit → filter to that user's ID to see every action they've taken.

One pattern runs through all four

Every destructive action (cancel, refund, ban, delete) triggers a confirmation dialog and an audit log row. If you can't find the dialog, check the role — you may not have permission.

A2 Appendix

Environment variables.

A production deployment expects the following to be populated. Grouped by concern so you know which system each connects to.

EventFlowA2 · Env vars

Core

DATABASE_URLPostgres connection string (Supabase or self-hosted).
NEXTAUTH_SECRET32+ character random string used to sign session JWTs.
NEXTAUTH_URLPublic URL your app is served at.
REDIS_URLOptional. Unlocks proper rate-limiting and the background email queue.

Email

RESEND_API_KEYTransactional email provider API key.
EMAIL_FROMFrom-address. In production the app refuses to send without it, to avoid SPF/DKIM failures.

Security

TICKET_SECRET32+ character HMAC secret used to sign QR payloads. Required — no fallback.
API_KEY_SALTSalt for hashing user-generated API keys.

Payments

RAZORPAY_KEY_ID / RAZORPAY_KEY_SECRETGateway credentials (India). Test keys work in dev.
RAZORPAY_WEBHOOK_SECRETUsed to verify incoming webhook calls.
STRIPE_SECRET_KEY / STRIPE_WEBHOOK_SECRETOptional, for Stripe-backed deployments.

OAuth

GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRETSign in with Google.
MICROSOFT_CLIENT_ID / MICROSOFT_CLIENT_SECRETSign in with Microsoft.
